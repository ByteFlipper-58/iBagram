# Руководство по синхронизации с апстримом Telegram (Upstream Sync Guide)

> **Статус:** Действующий регламент разработки  
> **Апстрим-репозиторий:** `upstream -> https://github.com/DrKLO/Telegram.git`  
> **Наш репозиторий:** `origin -> https://github.com/ByteFlipper-58/iBagram.git`

---

## 1. Концепция форка и архитектурная защита

Проект `iBagram` является долгосрочным форком официального клиента Telegram для Android (`DrKLO/Telegram`).
Для того чтобы проект мог развиваться годами и безболезненно получать официальные обновления Telegram из Дубая, кодовая база спроектирована по паттерну **Strangler Fig (Удушающий инжир)**:

```text
Официальный Telegram (upstream)
         │  (обновления в монолитных классах)
         ▼
MessagesController / SendMessagesHelper / Activity
         │
         ▼  ◄── [Единственная точка соприкосновения: LegacyRepository]
Наш доменный слой (Domain UseCases / Models)
         │  (100% изолирован от апстрима)
         ▼
Наш UI / ViewModels (StateFlow)
```

### Почему конфликтов будет минимум:
1. **Изоляция в каталоге `feature/`:** Все 105 архитектурных срезов вынесены в пакет `org.telegram.messenger.feature.<domain>.<feature>.*`. В официальном репозитории такой директории нет, поэтому файлы фичей **физически не получают merge-конфликтов** при слиянии с апстримом.
2. **Локализация изменений в адаптерах:** Если Telegram изменяет логику или сигнатуру метода в `MessagesController`, это **не ломает** 50 экранов приложения. Поломка локализуется строго в **одном файле** — `Legacy*Repository`. Правятся 2-3 строчки в адаптере данных, а доменный и презентационный слои остаются нетронутыми.
3. **Неприкасаемое ядро:** Мы принципиально не изменяем сетевой протокол MTProto, сериализацию TL (`TLRPC.java`), криптографию (`SRPHelper.java`) и нативный C++ движок (`jni/`).

## 2. Структура веток и тегов

* **`upstream/master`** и **`upstream/release-*`**: Чистый, неизменяемый апстрим Telegram.
* **`master`**: Основная стабильная ветка форка.
* **`refactor/architecture-v1`** (тег: `v1.0-architecture`):  
  **Эталонная база Фазы 1.** Содержит 105 изолированных архитектурных срезов, 7 доменов, 7 доменных DI-контейнеров и легкий фасад. Гарантированно компилируется и проходит все тесты на 100%. Изменения сюда больше не коммитятся.
* **`refactor/architecture-v2`**:  
  **Активная ветка Фазы 2 (UI Wiring).** В этой ветке мы подключаем созданные ViewModels к реальным экранам приложения (`DialogsActivity`, `ChatActivity`, `LaunchActivity`) и выдавливаем старый спагетти-код из UI.
* **`sync/upstream-<версия>`**:  
  Временные ветки для безопасного слияния конкретных обновлений Telegram.

## 3. Пошаговый регламент слияния обновлений (Runbook)

При выходе новой официальной версии Telegram выполните следующие шаги:

### Шаг 1. Проверка рабочего дерева
Убедитесь, что в рабочей ветке нет незакоммиченных изменений:
```bash
git status
```
Если есть незавершенная работа — закоммитьте её или сохраните в stash (`git stash`).

---

### Шаг 2. Получение обновлений из апстрима
Скачайте актуальные коммиты и релизные теги официального Telegram:
```bash
git fetch upstream --tags
```
Посмотрите список доступных релизных тегов:
```bash
git tag -l "release-*" --sort=-v:refname | head -n 10
```

---

### Шаг 3. Создание изолированной ветки слияния
**Никогда не делайте merge апстрима напрямую в рабочую ветку!** Всегда создавайте изолированную ветку:
```bash
git checkout -b sync/upstream-11.x refactor/architecture-v2
```

---

### Шаг 4. Запуск слияния
Запустите слияние с нужным релизным тегом (или веткой `upstream/master`):
```bash
git merge upstream/release-11.x
```

---

### Шаг 5. Разрешение конфликтов (Матрица решений)

При возникновении конфликтов руководствуйтесь следующими правилами:

| Компонент / Директория | Источник истины | Стратегия разрешения |
| :--- | :--- | :--- |
| **`TMessagesProj/.../feature/`** | **Ours (Наш код)** | Полностью сохраняем наши доменные фичи. Апстрим туда ничего не пишет. |
| **`TMessagesProj/.../core/di/`** | **Ours + Адаптация** | Сохраняем структуру фасада и доменных контейнеров. Если Telegram добавил новый глобальный контроллер, регистрируем его в соответствующем домене. |
| **`MessagesController`, `MediaDataController` и др.** | **Theirs (Апстрим)** | Принимаем изменения апстрима. Если мы вносили в эти классы мелкие вспомогательные методы — аккуратно переносим их. |
| **Экраны интерфейса (`ChatActivity.java`, `DialogsActivity.java`)** | **Theirs + Наши хуки** | Принимаем официальные изменения разметки и логики Telegram, сохраняя наши строки инициализации ViewModel (`AccountFeatureContainer.get(...)`) и подписки на `StateFlow` в `onFragmentCreate`/`onFragmentDestroy`. |
| **Ядро C++ / JNI (`jni/`, `libtgvoip/`)** | **Theirs (Апстрим)** | 100% апстрим без изменений. |
| **Ресурсы (`res/values/strings.xml` и др.)** | **Слияние** | Сохраняем новые строки Telegram + наши кастомные ключи. |

---

### Шаг 6. Адаптация репозиториев (если изменились методы контроллеров)

Если после слияния компилятор ругается на ошибки в `Legacy*Repository` (например, Telegram переименовал метод `MessagesController.deleteMessages` или добавил новый аргумент):
1. Откройте соответствующий адаптер в `TMessagesProj/src/main/java/org/telegram/messenger/feature/<domain>/<feature>/data/repository/Legacy*Repository.kt`.
2. Обновите вызов к методу Telegram в соответствии с новой сигнатурой.
3. Доменный интерфейс `*Repository` и `ViewModel` **НЕ меняются**.

---

### Шаг 7. Верификация сборки и тестов

Обязательно проверьте, что проект компилируется и все тесты зеленые:

1. **Компиляция Kotlin и Java:**
   ```bash
   .\gradlew.bat compileDebugKotlin compileDebugJavaWithJavac
   ```
2. **Прогон unit-тестов:**
   ```bash
   .\gradlew.bat testDebugUnitTest
   ```

---

### Шаг 8. Фиксация слияния в `refactor/architecture-v2`

После того как сборка и тесты успешно прошли:
```bash
git add -A
git commit -m "chore(upstream): merge Telegram release-11.x and adapt legacy repositories"
git checkout refactor/architecture-v2
git merge --ff-only sync/upstream-11.x
git push origin refactor/architecture-v2
git branch -d sync/upstream-11.x
```

## 4. Экстренный откат (Emergency Rollback)

Если слияние пошло не по плану, возникли неразрешимые конфликты или билд сломался:

1. **Отмена начатого слияния:**
   ```bash
   git merge --abort
   ```
2. **Возврат ветки слияния в исходное состояние:**
   ```bash
   git reset --hard refactor/architecture-v2
   ```
3. **Возврат к эталонной базе первой фазы (при любой катастрофе):**
   ```bash
   git checkout -B refactor/architecture-v2 v1.0-architecture
   ```
   *Тег `v1.0-architecture` гарантирует, что вы никогда не потеряете наработки первой фазы.*
